## 5. 开机 / 保活

| # | 场景 | 期望 | 结果 |
|---|------|------|------|
| B1 | 冷启 + 空闲开 + 未播歌 | 约 2.5/8/20s 内尽力恢复 | ⚠️ **已知限制**（见下） |
| B2 | 冷启 + 空闲开 + 已播歌 | 不占屏；停播后再上 | ➖ 依赖 B1 能冷启；当前不可测完整路径 |
| B3 | 冷启 + 空闲关 | 不抢屏 | ➖ 同上（冷启本就不拉起 = 满足「不抢」副作用） |
| B4 | 杀进程后亮屏 / 解锁 | 可恢复或进 App 一键应用 | ✅ 0.1.13 force-stop→开 App ~4s ClusterStrip |
| B5 | 电池优化忽略 | 关于页可跳转；忽略后开机更稳 | ⚠️ `dumpsys deviceidle whitelist +com.starlive.app` 可写入，**冷启仍无 BOOT**；需车机 UI「自启动」 |

### B1 结论（2026-08-03 · 0.1.12-car · 多次 reboot）

| 项 | 结果 |
|----|------|
| `adb reboot` 次数 | ≥4（含 0.1.11 ×2 + 本轮 ×2，用户确认） |
| 冷启后进程 / KeepAlive / ClusterStrip | **无** |
| `files/boot_probe.log` | **无**（`StartupReceiver` 未被调用） |
| Receiver 注册 / `RECEIVE_BOOT_COMPLETED` | 已注册、权限 granted |
| `deviceidle` 白名单（adb） | 可加入 `user,com.starlive.app`，**不能**换来冷启投递 BOOT |
| 根因判断 | **厂商自启策略拦截三方 App 的 BOOT**；非 App 调度逻辑缺陷 |
| 产品态度 | **暂不承诺冷启自启持久化**；**0.1.13+** 打开 App 一次即自动恢复上屏（process-start） |
| 解法（非代码） | 车机设置 → 自启动 / 关联启动 / 电池优化 **UI 白名单** 后，用 `boot_probe.log` 再验 |
| 代码补偿 | `StarLiveApp` → `bootScheduler.schedule("process-start")`；与 BOOT 共用 2.5/8/20s |

帮助文案 / [INSTALL.md](./INSTALL.md) 已提示依赖厂商白名单。
